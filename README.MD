# Описание проекта

В рамках лабораторной работы был разработан Python-пакет **streamstats** с интерфейсом командной строки (**CLI**).

Программа предназначена для чтения и анализа файлов с событиями (логами). Она обрабатывает файлы форматов **CSV** и **JSONL**, проверяет корректность данных и создаёт отчёт в формате JSON.

Программа позволяет:

- подсчитать общее количество событий;
- определить количество событий каждого уровня;
- подсчитать события по источникам;
- найти источники ошибок уровней `ERROR` и `CRITICAL`;
- определить самую раннюю и самую позднюю временные метки;
- объединить данные нескольких файлов в один отчёт;
- пропустить неправильные строки по запросу пользователя.

Поддерживается обработка CSV и JSONL как по отдельности, так и одновременно. Можно передать несколько файлов одного формата или объединить CSV и JSONL в одном анализе. Результат сохраняется в общий JSON-отчёт.

Для работы с командной строкой используется библиотека **Typer**, а для проверки входных данных — **Pydantic**.

Файлы обрабатываются последовательно, без загрузки всех событий в память.

# Возможности программы

## 1. Поддерживаемые форматы

Программа работает с двумя форматами входных файлов: **JSONL** и **CSV**. Их можно анализировать отдельно или вместе.

### JSONL

JSONL — формат, в котором каждая строка содержит отдельный JSON-объект.

Пример:

```jsonl
{"timestamp":"2026-10-18T12:00:00+00:00","level":"INFO","source":"auth","message":"вход"}
{"timestamp":"2026-10-18T12:01:00+00:00","level":"ERROR","source":"auth","message":"ошибка входа"}
```

В обычном JSON события могут храниться в одном массиве объектов, а в JSONL каждый объект записан на отдельной строке. Поэтому строки JSONL можно читать и обрабатывать по очереди.

### CSV

CSV (*Comma-Separated Values* — значения, разделённые запятыми) — формат, в котором данные записываются в виде строк, а значения обычно разделяются запятыми.

Пример:

```csv
timestamp,level,source,message
2026-10-18T12:00:00+00:00,INFO,auth,вход
2026-10-18T12:01:00+00:00,ERROR,auth,ошибка входа
```

Первая строка содержит названия столбцов. Следующие строки — данные событий.

Для правильной обработки файла должны присутствовать обязательные столбцы.

## 2. Структура события

Каждое событие состоит из четырёх полей.

| Поле | Описание |
|---|---|
| `timestamp` | Дата и время события в формате ISO 8601 с часовым поясом |
| `level` | Уровень события |
| `source` | Источник, от которого получено событие |
| `message` | Текст сообщения |

Поддерживаются пять уровней:

- `DEBUG` — отладочная информация;
- `INFO` — обычное информационное сообщение;
- `WARNING` — предупреждение;
- `ERROR` — ошибка;
- `CRITICAL` — критическая ошибка.

Поле `source` не может быть пустым или состоять только из пробелов.

Поле `message` должно содержать строку.

## 3. Отчёт

После обработки файлов программа создаёт JSON-отчёт.

Он содержит:

1. Общее количество правильных событий.
2. Количество событий каждого уровня.
3. Количество событий по каждому источнику.
4. Количество ошибок `ERROR` и `CRITICAL` отдельно для каждой пары «источник — уровень».
5. Пять записей с наибольшим количеством ошибок.
6. Самую раннюю временную метку.
7. Самую позднюю временную метку.
8. Количество пропущенных неправильных строк.

При формировании топ-5 сначала учитывается количество ошибок. Если количество одинаковое, уровень `CRITICAL` имеет приоритет над `ERROR`.

# Описание алгоритма решения задачи

## 1. Чтение файлов

1. Пользователь запускает команду `python -m streamstats analyze` и указывает один или несколько файлов.
2. Через параметр `--format` передаётся формат входных данных.
3. Функция `read_events()` выбирает подходящий парсер для каждого файла.
4. Для CSV вызывается `parse_csv()`, для JSONL — `parse_jsonl()`.
5. Парсер последовательно читает строки и передаёт данные на проверку.

## 2. Проверка событий

1. Данные строки передаются в функцию `validate_event()`.
2. С помощью класса `Event` проверяется наличие и правильность полей.
3. Проверяются уровень события, временная метка и источник.
4. Если данные правильные, создаётся объект класса `Event`.
5. Если обнаружена ошибка, программа либо останавливается, либо пропускает неправильную строку в зависимости от выбранного режима.

## 3. Анализ событий

1. Функция `analyze()` получает поток проверенных событий.
2. Для каждого события увеличивается общий счётчик.
3. Обновляется количество событий соответствующего уровня.
4. Обновляется количество событий от соответствующего источника.
5. Если уровень равен `ERROR` или `CRITICAL`, дополнительно обновляется счётчик ошибок.
6. В процессе обработки определяются самая ранняя и самая поздняя даты.
7. После окончания чтения данные сортируются по количеству ошибок и выбираются первые пять записей.

## 4. Формирование отчёта

1. Функция `report()` получает результаты анализа.
2. Данные преобразуются в словарь, который можно сохранить в JSON.
3. Объекты даты и времени переводятся в строки с помощью `isoformat()`.
4. К отчёту добавляется количество пропущенных строк.
5. В `__main__.py` словарь записывается в файл с помощью `json.dump()`.
6. После сохранения отчёта программа выводит сообщение с путём к нему.

# Принятые решения при реализации проекта

Во время разработки проекта возникали вопросы, связанные с чтением файлов, проверкой данных, обработкой ошибок и работой командной строки. Для их решения были выбраны следующие способы.

## 1. Разделение программы на модули

Программа была разделена на несколько файлов, чтобы каждая часть выполняла отдельную задачу.

| Файл | Назначение |
|---|---|
| `models.py` | Класс события и проверка полей |
| `parsers.py` | Чтение файлов CSV и JSONL |
| `analysis.py` | Подсчёт статистики |
| `report.py` | Подготовка словаря отчёта |
| `errors.py` | Собственные классы исключений |
| `constants.py` | Хранение постоянных значений |
| `__main__.py` | Работа командной строки и сохранение отчёта |

Такое разделение позволяет не хранить весь код в одном файле. Благодаря этому проще находить нужные функции, исправлять ошибки и тестировать отдельные части программы.

## 2. Использование констант

Для хранения постоянных значений был создан отдельный файл `constants.py`.

В него вынесены:

- `REQUIRED_FIELDS` — обязательные поля CSV-файла;
- `LEVEL_PRIORITY` — приоритет уровней `ERROR` и `CRITICAL` при сортировке;
- `TOP_SOURCES_LIMIT` — максимальное количество записей в топе ошибок.

Это позволяет хранить постоянные значения отдельно от основного кода. Если потребуется изменить одно из них, достаточно исправить его в `constants.py`.

## 3. Использование генераторов для чтения файлов

Одним из основных требований лабораторной работы была обработка файлов без загрузки всех событий в память.

Поэтому в парсерах и функции `read_events()` используется `yield`.

Вместо создания общего списка событий функции последовательно передают по одному объекту `Event`.

Это позволяет анализатору обрабатывать данные сразу после чтения.

Такой способ особенно полезен при работе с большими файлами, поскольку не требуется хранить все события одновременно.

При этом словари со статистикой остаются в памяти, так как в них накапливаются результаты подсчёта.

## 4. Различие между JSON и JSONL

При реализации JSONL-парсера нужно было учитывать, что JSON и JSONL имеют разную структуру.

В обычном JSON события могут находиться в одном массиве объектов, а в JSONL каждый объект записывается отдельно, на новой строке.

Поэтому было решено использовать `json.loads()` для каждой прочитанной строки, а не загружать файл целиком через `json.load()`.

Это также позволяет определить номер неправильной строки и продолжить чтение остальных событий в режиме `--skip-invalid`.

## 5. Чтение CSV через `csv.DictReader`

При работе с CSV важно правильно учитывать первую строку, в которой записаны названия столбцов.

Для этого был выбран `csv.DictReader()`.

Он использует заголовок файла и возвращает данные каждой записи в виде словаря.

Благодаря этому поля можно получать по названиям `timestamp`, `level`, `source`, `message`, а не по их номерам.

Дополнительно проверяется наличие обязательных столбцов и обнаруживаются строки с лишними значениями.

## 6. Использование Pydantic для проверки событий

Для проверки входных данных была выбрана библиотека Pydantic.

В файле `models.py` создан класс `Event`, который наследуется от `BaseModel` библиотеки Pydantic. В этом классе указаны обязательные поля события и их типы.

При создании объекта `Event` Pydantic проверяет полученные значения.

Отдельно проверяется поле `source`, поскольку строка из одних пробелов не должна считаться правильным источником.

Использование Pydantic позволило не писать все проверки типов вручную.

## 7. Обработка неправильных строк

В программе предусмотрены два режима обработки ошибок.

По умолчанию при обнаружении неправильной строки обработка останавливается.

Если пользователь указывает `--skip-invalid`, программа записывает предупреждение и переходит к следующей строке.

Для этого используется `continue`.

Такое решение позволяет пользователю самостоятельно выбрать: остановить анализ при первой ошибке или получить статистику по всем правильным событиям.

## 8. Общий счётчик пропущенных строк

При обработке нескольких файлов необходимо учитывать общее количество пропущенных строк.

Для этого используется словарь:

```python
skip_lines = {"skip_lines": 0}
```

Он передаётся парсерам, которые увеличивают значение при пропуске неправильной строки:

```python
skip_lines["skip_lines"] += 1
```

Словарь был выбран потому, что это изменяемый объект. Все парсеры могут изменять один общий счётчик.

После завершения обработки полученное значение добавляется в отчёт.

## 9. Использование собственных исключений

Для обработки разных ошибок был создан файл `errors.py`.

В нём находится общий класс `StreamStatsError` и отдельные классы для неправильных данных, временных меток, неподдерживаемого формата и ошибок параметров CLI.

Также используется `InvalidLineError`, который хранит путь к файлу, номер строки и причину ошибки.

Это позволяет выводить пользователю более понятные сообщения и определять, на каком этапе возникла проблема.

При ожидаемых ошибках консольная команда завершается с кодом `2`.

## 10. Использование логгера

Для записи ошибок и предупреждений применяется модуль `logging`.

По требованию проверки Ruff вместо прямого использования корневого логгера был создан отдельный логгер для каждого нужного модуля:

```python
logger = logging.getLogger(__name__)
```

Сообщения о пропущенных строках записываются с уровнем `WARNING`, а ошибки, из-за которых анализ останавливается, — с уровнем `ERROR`.

## 11. Использование Typer и команды `analyze`

Для интерфейса командной строки была выбрана библиотека Typer.

Она позволяет задавать аргументы файлов, опции и автоматически формировать справку.

При разработке возникла проблема с запуском единственной команды `analyze`.

Если приложение Typer содержит только одну команду, библиотека может использовать её как основную. Из-за этого при вводе `analyze` в терминале она не распознавалась как отдельная команда.

Для решения была добавлена функция:

```python
@app.callback()
def main() -> None:
    '''пустая функция тк если задана всего одна analyze то при вводе в терминал, название команды считывается как опция
    main сохраняет analyze как отдельную команду тайпер'''
```

`Callback` — это функция, которую Typer может вызвать перед выполнением команды. В нашем случае `main()` ничего дополнительно не делает, но её регистрация через `@app.callback()` позволяет сохранить `analyze` как отдельную команду.

В результате программа запускается в формате, указанном в задании:

```bash
python -m streamstats analyze logs.jsonl --format jsonl
```

## 12. Обработка нескольких файлов

Программа может принимать сразу несколько входных файлов.

Пользователь может указать один формат для всех файлов:

```bash
python -m streamstats analyze first.jsonl second.jsonl --format jsonl
```

Или отдельный формат для каждого файла:

```bash
python -m streamstats analyze first.csv second.jsonl --format csv --format jsonl
```

Для сопоставления файлов и форматов в функции `read_events()` используется `enumerate()`.

Если передан один формат, он применяется ко всем файлам. Если указано несколько форматов, каждый выбирается по индексу соответствующего файла.

Дополнительно проверяется правильность количества переданных форматов.

## 13. Подсчёт статистики с помощью словарей

Для подсчёта событий используются словари.

Количество событий каждого уровня хранится в `level_counts`, а количество событий по источникам — в `source_counts`.

При подсчёте источников применяется метод `.get()`, чтобы при первом появлении нового источника начинать счёт с нуля.

Для ошибок `ERROR` и `CRITICAL` используются составные ключи:

```python
(source, level)
```

Это позволяет отдельно учитывать разные уровни ошибок одного источника.

## 14. Сортировка ошибок и формирование топ-5

Для получения пяти записей с наибольшим количеством ошибок используется функция `sorted()`.

Сортировка выполняется по количеству ошибок в порядке убывания.

При одинаковом количестве был добавлен приоритет уровней:

```python
LEVEL_PRIORITY = {"CRITICAL": 2, "ERROR": 1}
```

Это позволяет расположить `CRITICAL` выше `ERROR`, если количество ошибок одинаковое.

После сортировки с помощью среза `[:TOP_SOURCES_LIMIT]` выбираются первые пять записей. Значение `TOP_SOURCES_LIMIT` хранится в файле `constants.py` и равно `5`.

## 15. Поиск самой ранней и самой поздней даты

При обработке первого события его дата сохраняется одновременно как минимальная и максимальная.

Далее время каждого события сравнивается с текущими значениями.

Такой способ позволяет найти нужные даты за один проход по событиям.

## 16. Формирование JSON-отчёта

Функция `analyze()` из файла `analysis.py` возвращает проанализированные данные, а `report.py` преобразует их в словарь для сохранения.

Составные ключи `(source, level)` переводятся в список словарей, потому что JSON не поддерживает кортежи в качестве ключей объектов.

Объекты `datetime` преобразуются в строки с помощью `isoformat()`.

Для записи отчёта используется:

```python
json.dump(result, file, ensure_ascii=False, indent=4)
```

Параметр `ensure_ascii=False` позволяет сохранять русские символы в читаемом виде.

`indent=4` добавляет отступы, чтобы содержимое отчёта было удобнее просматривать.

## 17. Проверка совпадения файлов

При реализации CLI была добавлена проверка совпадения входного и выходного путей.

Если пользователь пытается сохранить отчёт в исходный файл, программа завершает работу с ошибкой.

Для сравнения используется метод `.resolve()`, который позволяет получить абсолютные пути.

Это сделано для того, чтобы случайно не удалить исходные данные при открытии выходного файла в режиме записи.

## 18. Автоматическое тестирование и проверки кода

Для тестирования используется pytest.

Отдельно проверяются парсеры, ошибки, пустые файлы, обработка нескольких файлов, Unicode и запуск CLI.

Для интеграционных тестов применяется `CliRunner`, который позволяет проверить выполнение консольной команды без отдельного ручного запуска в терминале.

В тестах также используются:

- `tmp_path` — для создания временных файлов;
- `caplog` — для проверки сообщений логгера;
- `pytest.raises()` — для проверки ожидаемых исключений;
- `assert` — для сравнения полученных и ожидаемых результатов.

Дополнительно были настроены Ruff, mypy и pre-commit.

Во время проверки возникали замечания Ruff, связанные с использованием корневого логгера. Они были исправлены с сохранением основной логики программы.

# Обработка ошибок

Программа проверяет входные данные и параметры командной строки.

Основные обрабатываемые ситуации:

| Ошибка | Пример |
|---|---|
| Неподдерживаемый формат | `--format txt` |
| Неправильный JSONL | Строка `not json` |
| Отсутствует обязательное поле | Нет `source` |
| Неизвестный уровень события | `level = "unknown"` |
| Неправильная временная метка | `timestamp = "не дата"` |
| Пустой источник | `source = ""` |
| Источник из пробелов | `source = "   "` |
| Отсутствует обязательный столбец CSV | Нет столбца `timestamp` |
| Лишние значения в строке CSV | Значений больше, чем столбцов |
| Неправильное количество форматов | Один файл и два `--format` |
| Отсутствует входной файл | `missing.jsonl` |
| Входной и выходной файл совпадают | Один путь для `INPUT` и `--output` |

Если возникает ошибка без режима `--skip-invalid`, программа сообщает причину и завершает работу с кодом `2`.

При ошибках отдельных строк в режиме `--skip-invalid` программа продолжает работу, записывает предупреждение `WARNING` и учитывает пропущенную строку в статистике.

Ошибки в параметрах запуска, например неправильное количество форматов, нельзя пропустить с помощью этого флага.

# Описание файлов проекта

### `models.py`

Содержит класс `Event`, который описывает структуру события и проверяет корректность его полей.

### `parsers.py`

Содержит функции `parse_jsonl()` и `parse_csv()` для чтения входных файлов, а также `validate_event()` для проверки данных и создания объектов событий.

### `analysis.py`

Содержит функцию `analyze()`, которая подсчитывает статистику по событиям, формирует топ-5 ошибок и определяет временные границы.

### `report.py`

Содержит функцию `report()`, которая преобразует результаты анализа в словарь для последующего сохранения в JSON.

### `constants.py`

Содержит обязательные поля CSV, приоритет уровней ошибок и ограничение количества записей в топе.

### `errors.py`

Содержит классы исключений для различных ошибок, возникающих при чтении и обработке файлов.

### `__main__.py`

Создаёт интерфейс командной строки с помощью Typer, обрабатывает параметры пользователя, вызывает остальные функции и сохраняет отчёт.

### `tests/`

Содержит unit-тесты отдельных функций и интеграционные тесты командной строки.

### `pyproject.toml`

Содержит сведения о проекте, его зависимостях и настройки инструментов проверки кода.

### `.pre-commit-config.yaml`

Содержит настройки проверок, которые могут автоматически запускаться перед созданием коммита.

# Примеры работы программы

## 1. Анализ одного JSONL-файла

```bash
python -m streamstats analyze logs.jsonl --format jsonl --output REPORT.json
```

**Вывод:**

```text
отчёт сохранён: REPORT.json
```

В результате создаётся файл `REPORT.json` с данными анализа событий.

## 2. Анализ CSV-файла

```bash
python -m streamstats analyze logs.csv --format csv --output REPORT.json
```

Программа читает строки CSV, проверяет обязательные поля и сохраняет отчёт.

## 3. Анализ нескольких JSONL-файлов

```bash
python -m streamstats analyze first.jsonl second.jsonl --format jsonl --output REPORT.json
```

В данном случае формат указывается один раз, поскольку оба файла имеют одинаковый формат.

## 4. Анализ файлов разных форматов

```bash
python -m streamstats analyze logs.csv logs.jsonl --format csv --format jsonl --output REPORT.json
```

Программа последовательно обработает CSV и JSONL, а затем сформирует один общий отчёт.

## 5. Пропуск неправильных строк

```bash
python -m streamstats analyze logs.jsonl --format jsonl --skip-invalid --output REPORT.json
```

Если в файле встречаются неправильные строки, программа записывает предупреждения, пропускает их и продолжает анализ.

Количество таких строк сохраняется в поле `skip_lines`.

## 6. Пример готового отчёта

Исходный файл содержит два события: одно уровня `ERROR` от `auth`, второе уровня `CRITICAL` от `database`.

Тогда отчёт будет выглядеть так:

```json
{
    "count_event": 2,
    "level_count": {
        "INFO": 0,
        "DEBUG": 0,
        "WARNING": 0,
        "ERROR": 1,
        "CRITICAL": 1
    },
    "source_counts": {
        "auth": 1,
        "database": 1
    },
    "level_source_counts": [
        {
            "source": "auth",
            "level": "ERROR",
            "count": 1
        },
        {
            "source": "database",
            "level": "CRITICAL",
            "count": 1
        }
    ],
    "top_5_source": [
        {
            "source": "database",
            "level": "CRITICAL",
            "count": 1
        },
        {
            "source": "auth",
            "level": "ERROR",
            "count": 1
        }
    ],
    "earliest_timestamp": "2026-10-18T12:00:00+00:00",
    "latest_timestamp": "2026-10-18T13:00:00+00:00",
    "skip_lines": 0
}
```

Здесь общее количество событий равно двум. Ошибки принадлежат разным источникам, а в рейтинге `CRITICAL` расположен выше `ERROR` при одинаковом количестве.

Если событий нет, самые ранняя и поздняя даты в отчёте имеют значение `null`.

# Запуск программы

## Общий вид команды

```bash
python -m streamstats analyze INPUT --format FORMAT --output REPORT.json
```

Где:

- `INPUT` — путь к файлу, который нужно проанализировать;
- `FORMAT` — формат входного файла: `csv` или `jsonl`;
- `REPORT.json` — путь для сохранения отчёта.

Можно указать несколько входных файлов:

```bash
python -m streamstats analyze INPUT1 INPUT2 --format FORMAT --output REPORT.json
```

Параметр `--output` необязательный. Если его не указывать, отчёт будет сохранён в файл `REPORT.json` в текущей рабочей папке.

## Дополнительный параметр

Для пропуска неправильных строк:

```bash
--skip-invalid
```

Без этого параметра обработка останавливается при первой неправильной строке.

## Справка по программе

```bash
python -m streamstats --help
```

Справка по команде анализа:

```bash
python -m streamstats analyze --help
```

Эти команды позволяют посмотреть доступные команды, аргументы и опции программы.
